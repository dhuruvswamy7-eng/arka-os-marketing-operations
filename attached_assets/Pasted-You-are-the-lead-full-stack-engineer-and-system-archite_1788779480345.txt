You are the lead full-stack engineer and system architect for **ARKA OS**, an internal Work Intelligence & Operations System for Arka Digital Media.

Your job is to build a REAL, production-quality internal web application in code — not a mockup, not a static prototype, and not a collection of disconnected screens.

## 1. PRODUCT DEFINITION

ARKA OS is Arka Digital Media's internal operating system for managing:

* People
* Work
* Task ownership
* Deadlines
* Progress
* Time / effort
* Workload
* Bottlenecks
* Founder visibility
* Operational intelligence

Core principle:

**PEOPLE → WORK → ASSIGNMENT → DEADLINE → PROGRESS → TIME / EFFORT → BOTTLENECKS → FOUNDER INSIGHT**

The product is NOT primarily an attendance tracker, surveillance tool, content calendar, or CRM.

The first objective is to create one reliable internal system of record for people, work and operational time.

Do not introduce unnecessary modules until the core workflow is working.

# 3. DEVELOPMENT PRINCIPLES

Follow these rules throughout the project:

1. Build one phase at a time.
2. Build real functionality, not fake demo interactions.
3. Keep the database model minimal.
4. Use reusable components.
5. Use TypeScript properly.
6. Do not hard-code operational data.
7. Do not create fake dashboard metrics and present them as real.
8. Use realistic empty states when there is no data.
9. Validate all forms.
10. Handle loading, error and empty states.
11. Protect authenticated routes.
12. Enforce authorization at the database level using RLS.
13. Never rely only on frontend hiding for security.
14. Keep Founder/Admin visibility broader than normal team members.
15. Do not over-engineer future features.
16. Do not add a feature just because it looks impressive.
17. Every feature must have a clear operational purpose.
18. Preserve a clean architecture so later modules can be added without rebuilding the foundation.

# 5. DATABASE ARCHITECTURE

Start with these tables.

## users

Fields:

* id
* org_id
* role
* name
* email
* created_at
* updated_at

The user should be linked appropriately to Supabase Auth.

Roles:

* founder_admin
* manager
* team_member

## login_logs

Fields:

* id
* user_id
* login_at
* logout_at

Capture login/logout activity automatically where technically appropriate.

## tasks

Fields:

* id
* org_id
* title
* description
* assignee_id
* status
* priority
* due_date
* created_by
* created_at
* updated_at
* completed_at

Also design:

* client_id nullable
* campaign_id nullable

These should remain optional so future client/campaign relationships can be introduced without redesigning the task architecture.

## task_activity

Fields:

* id
* task_id
* old_status
* new_status
* old_assignee_id nullable
* new_assignee_id nullable
* changed_by
* changed_at

Use this to create an operational history.

## time_entries

Fields:

* id
* task_id
* user_id
* start_time
* end_time
* duration_minutes
* created_at

Time must be attributable to an actual task.

Do NOT create a generic "employee hours" system disconnected from work.

# 11. OPERATIONAL INTELLIGENCE

After the basic dashboard works, introduce simple intelligence based ONLY on real data.

* Active tasks
* Priority
* Upcoming deadlines
* Overdue work
* Logged effort

Display:

* Low
* Medium
* High
* Overloaded

Do not pretend this is an exact employee-capacity calculation.

Clearly label it as an operational indicator.

## Bottleneck detection

Identify:

* Overdue tasks
* Blocked tasks
* Tasks with no recent activity
* High concentrations of work
* Tasks approaching deadline without progress

Example:

### Bottleneck detected

"Manager Review"

8 tasks are currently waiting for review.

This should be based on actual database data.

* Roles work correctly.

* Time can be started/stopped.
* Manual time can be recorded.
* Time is linked to tasks.

PHASE 4 is complete when:

* Founder has one operational dashboard.
* Workload is visible.
* Overdue work is visible.
